## 2. API ↔ DB 통합 테스트

### 2.1 방법

1. `docker compose`로 실제 MySQL 8.4와 Spring Boot 서버를 띄웁니다. (H2·Mock 없이 운영과 같은 구성)
2. 테스트 스크립트(`scripts/qa/integration_test.py`)가 사용자 A·B 두 계정을 만들어 57개 API를 차례로 호출합니다.
3. 각 호출의 **HTTP 상태 코드, 에러 코드, 응답 본문의 핵심 값**을 기대값과 비교합니다.
4. 저장·수정·삭제 API는 `docker exec mysql`로 **DB 행을 직접 조회**해서 실제로 반영됐는지 확인합니다.
5. 테스트가 끝나면 두 계정을 회원 탈퇴시켜, 종속 데이터까지 함께 지워지는지도 검증합니다.

## 3. Front ↔ Back 연동 테스트

### 3.1 방법

Expo 웹 앱을 **실제 서버 모드**(`EXPO_PUBLIC_USE_MOCKS=false`)로 실행하고, 데모 계정(`scripts/qa/seed_demo.py`로 API를 통해 생성)으로 로그인했습니다. 화면별로 **브라우저 네트워크 로그의 API 호출**과 **표시된 값이 서버 데이터와 같은지**를 확인했습니다. 화면 크기는 375×812(모바일)입니다.

### 3.3 연동 중 발견한 문제

| ID | 내용 | 조치 |
|---|---|---|
| ISSUE-007 | `.env.local`의 `EXPO_PUBLIC_USE_MOCKS=true`가 셸 환경변수보다 우선해서, 서버 모드로 실행해도 **API 호출이 0건**이었음 (시연 데이터로 동작) | `.env.development.local`로 덮어쓰는 절차 문서화 |

| BUG-005 | 커뮤니티 작성 시각이 `2026-10-14T10:15:52.249502Z`로 표시 | 수정 · '3분 전'으로 표시 확인 |
| ISSUE-008 | 앱 시작 시 `dashboard`·`records`가 2번씩 호출되고, 로그인 전 401 호출 2건 발생 | 미해결 (성능·로그 문제, 기능 영향 없음) |

## 4. 실제 서버 추가 검증 (11/03)

### 4.1 AI 사진 분석 (가짜 Gemini 서버)

| 상황 | 응답 | 확인 내용 |
|---|---|---|
| 정상 인식 | 200 | 사진·키 전송, DB 저장, 식단 저장 후 홈 칼로리 352 반영 |
| 커뮤니티 사진 분석 | 200 | 식단과 같은 분석기 결과 합산 |
| 호출량 초과 (Gemini 429) | 503 NET_001 | 안내 문구 반환 |
| 음식 없는 사진 | 502 AI_001 | 저장하지 않음 |

서버 로그에 API 키가 찍히지 않는 것도 확인했습니다. **실제 Gemini 호출은 키가 없어 아직 확인하지 못했습니다.**

## 5. 결론

- 57개 API 모두 정상·예외·권한 케이스를 통과했고, 저장 계열 API는 DB 반영까지 확인했습니다.
- 1차 실행에서 발견한 **서버 500 오류(BUG-001)를 수정**하고 회귀 테스트로 재발을 막았습니다.
- 화면 8개가 실제 서버 데이터를 읽고 쓰는 것을 확인했으며, 시연 데이터에서는 드러나지 않던 **화면 오류 2건을 발견해 수정**했습니다.
