# 01. 테스트 계획서

## 1. 목적

5주차 피드백(테스트·디버깅 진행)에 따라, 구현된 기능이 **명세대로 동작하는지 수치로 확인**하고 발견한 결함을 **원인 분석 → 수정 → 회귀 테스트** 순서로 처리한다.

## 2. 범위

| 구분 | 대상 | 비고 |
|---|---|---|
| 백엔드 | 57개 REST API (명세서 54개 + 추가 3개), 서비스 로직, 예외 처리 | Spring Boot 3.5 / Java 17 |
| 데이터베이스 | MySQL 8.4, 23개 테이블 | API 호출 후 DB 값을 직접 조회해 검증 |
| 프론트엔드 | Expo 웹 빌드 (React Native 0.86), 주요 8개 화면 | 실제 서버 연결 모드 |
| 제외 | 외부 비전 AI, 지도 API, 푸시 발송, 실시간 가격 API | 미연동 기능이라 대체 로직만 확인 |

## 3. 테스트 단계와 방법

| 단계 | 목적 | 방법 · 도구 | 산출물 |
|---|---|---|---|
| 단위 테스트 | 함수·서비스 로직 검증 | JUnit 5, Mockito, MockMvc(standalone), JaCoCo / TypeScript `tsc`, ESLint | 단위 테스트 리포트 |
| 통합 테스트 ① API↔DB | 컨트롤러~DB 전체 경로 검증 | 실행 중인 서버에 HTTP 요청 → 응답 코드·본문 확인 → `docker exec mysql`로 DB 값 확인 (Python 스크립트) | 통합 테스트 결과서 |
| 통합 테스트 ② Front↔Back | 앱 화면이 실제 서버 데이터를 표시·저장하는지 검증 | Expo 웹 + 내장 브라우저(375×812), 네트워크 요청 로그와 화면 캡처 | 통합 테스트 결과서 |
| 시스템 테스트 | 사용자 시나리오 전체 흐름(End-to-End) 검증 | 실제 사용자 순서대로 여러 기능을 연결해 호출하고, 앞 단계 결과가 다음 화면 데이터에 반영되는지 확인 | 시스템 테스트 결과서 |
| 회귀 테스트 | 수정이 다른 기능을 깨뜨리지 않았는지 확인 | 버그마다 재현 테스트 추가 후 전체 재실행, CI에서 자동 실행 | 버그/이슈 리포트 |

## 4. 테스트 케이스 설계 기준

- **정상 케이스**: API마다 최소 1건. 응답 코드와 핵심 필드 값을 함께 검증한다.
- **예외 케이스**: 입력 형식 오류(400), 인증 없음·위조 토큰(401), 타인 리소스 접근(403/404), 없는 리소스(404), 중복(409).
- **DB 검증**: 저장·수정·삭제 API는 응답만 믿지 않고 DB 행을 직접 조회한다. (예: 식단 총 칼로리 = 항목 합계)
- **권한 검증**: 사용자 A·B 두 계정으로 남의 식단·재료·게시글·댓글을 수정·삭제할 수 없는지 확인한다.
- **경계값**: 목표 칼로리 80% 미만/100% 초과(토마토 상태), 월 0·13, 위도 범위 밖, 페이지 크기 999.

## 5. 합격 기준

| 항목 | 기준 |
|---|---|
| 단위 테스트 | 실패 0건 |
| 통합 테스트 | 57개 API 모두 정상·예외 케이스 통과, 서버 500 응답 0건 |
| 시스템 테스트 | 모든 시나리오의 모든 단계 통과 |
| 결함 | Critical/Major 결함은 수정 + 회귀 테스트 추가, 미해결 건은 사유와 담당 명시 |

## 6. 테스트 환경

| 항목 | 값 |
|---|---|
| OS | macOS (Apple Silicon) |
| 컨테이너 | Docker 29.7.2, `docker compose` (mysql:8.4, 백엔드 이미지 직접 빌드) |
| 백엔드 빌드 | eclipse-temurin:17-jdk 컨테이너, Gradle 8.14.3 |
| 프론트 | Expo SDK 57 웹, `EXPO_PUBLIC_USE_MOCKS=false` |
